# 開発体制とDefinition of Done / Ready

このドキュメントは「誰が」「どうなったら着手してよく」「どうなったら完了と言えるか」を
決めておくためのものです。初めてアジャイル開発をする方向けに、用語の説明から書いています。

## 1. 開発体制

| 役割 | 担当 | やること |
|---|---|---|
| 開発者 | あなた + Claude（AIアシスタント） | 要件の相談、実装、動作確認、ドキュメント更新 |
| 監修者 | 給与計算に詳しい方（氏名未定） | 俸給表の数値・手当の計算式・法令の解釈など、**給与制度として正しいか**のレビュー |

ポイントは、「動くかどうか」は開発者（あなた+Claude）が確認し、「制度として正しいかどうか」は
監修者が確認する、という役割分担です。片方だけでは正しいツールになりません。

監修者がまだ決まっていない場合は、バックログやスプリント記録に「監修待ち」「監修者未依頼」と
書いておき、依頼できたタイミングでステータスを更新してください。

## 2. Definition of Ready（着手してよい条件）

これは「プロダクトバックログの項目（PBI）に着手し始めてよい」と判断するためのチェックリストです。
全部埋まっていなくても着手はできますが、埋まっていない項目は「不明点」として残しておきましょう。

- [ ] 何を実現したいか、1〜2文で説明できる
- [ ] 参考にする制度・法令・出典（人事院規則、給与法など）が分かっている。
      分からない場合は「不明。監修者に確認する」と明記されている
- [ ] この項目が**監修（給与制度として正しいかのチェック）を必要とするか**が分かっている
- [ ] どのファイルを触りそうか、だいたいの見当がついている

## 3. Definition of Done（完了と言える条件）

これは「この作業は終わった」と自信を持って言うためのチェックリストです。
特に、給与計算という性質上、「動くこと」と「制度として正しいこと」の両方を意識しています。

- [ ] 実装した機能がブラウザで実際に動作することを確認した
      （このプロジェクトではPlaywright等での自動確認、またはスクリーンショットでの目視確認を行っています）
- [ ] 計算式や金額を変更した場合、手計算やテストスクリプトで数値が合っていることを確認した
- [ ] **給与制度に関わる数値・計算式・出典を変更した場合、監修者にレビューを依頼した**
      （まだ依頼できていない場合は、プロダクトバックログに「監修待ち」と明記する）
- [ ] `README.md` や `docs/requirements.md` など、関連するドキュメントを更新した
- [ ] 変更内容を `CHANGELOG.md` に記録した
- [ ] 指定のブランチにコミット・pushした

## 4. 監修依頼の書き方（メモ程度でOK）

監修者に確認してもらうときは、次の3点だけ伝われば十分です。難しく考えなくて大丈夫です。

1. **どこを見てほしいか**（例：「超過勤務手当の割増率の表」）
2. **今の実装がどうなっているか**（例：「月60時間を超えたら平日は150%、深夜は175%にしています」）
3. **不安な点・確認したい点**（例：「60時間の判定に休日勤務を含めるべきか自信がありません」）

回答をもらったら、`docs/product-backlog.md` の該当項目のステータスを更新し、
必要であれば `docs/requirements.md` の「既知の制約」からその項目を削除してください。
